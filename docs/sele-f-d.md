# Sele 核心概念模型 v1.0

> 本文档补充规范 v1.0 未系统化的**概念语义**。规范定义"有什么"，本文定义"意味着什么"。
> 不涉及语言、库、文件格式细节。所有规则以概念层表述。

## 一、系统心智模型

### 1.1 Sele 本质

Sele 维护三样东西：

| 对象 | 语义 |
|---|---|
| **意图** | 人/agent 声明的"要达成什么"（Plan/Line 的 goal、acceptance） |
| **进度** | 当前推进到哪、被谁推进、因何暂停 |
| **证据** | 每次推进产生的可追溯、可验证的记录（事件日志） |

三者缺一不可：没有意图，进度无方向；没有进度，意图不推进；没有证据，进度不可信。

### 1.2 三个不变量（Invariants）

系统在任何时刻必须满足：

| # | 不变量 | 破坏后果 |
|---|---|---|
| **I1 单活跃** | 全局至多一个 Task 处于 `in_progress` | 物理并发，状态互相污染 |
| **I2 单步活跃** | 单个 Task 内至多一个 Step 处于 `in_progress` | Step 顺序语义被破坏 |
| **I3 事件完备** | 任何状态/属性变更必有对应事件记录 | 审计链断裂，状态不可重放 |

**任何命令执行前后都必须保持 I1–I3 成立**。若不成立，命令必须拒绝执行而非"尽力修复"。

### 1.3 时间与顺序

Sele **不用时间组织推进**，用顺序和依赖组织。

- 时间戳仅作审计用途，不参与决策。
- 暂停警告用"跳过计数"而非时间流逝。
- `sele next` 用拓扑序而非优先级/时间。
- 时间只用于事件日志的 `ts` 与排序。

**理由**：agent 的执行节奏不受日历支配，用时间做阈值会在"agent 休假一周"和"密集执行 1 小时"之间产生荒谬的语义。

## 二、工作循环模型

### 2.1 一次完整循环

Agent 与 Sele 的交互是一个固定循环：

```
┌───────────────────────────────────────────────┐
│ 1. 感知：sele next / sele status              │  ← 我现在该做什么
│ 2. 启动：sele task start <id>                 │  ← 进入工作状态
│ 3. 推进：sele step start/done、sele git commit │  ← 逐步执行
│ 4. 反馈：sele task pause/done/fail            │  ← 退出工作状态
│ 5. 记录：sele decision record（如遇岔路）      │  ← 留下决策痕迹
└───────────────────────────────────────────────┘
        ↑                                │
        └──────────── 循环 ──────────────┘
```

**核心约束**：

- 每一步都以**显式命令**驱动，不存在"隐式推进"。
- 感知阶段只读，不改变状态。
- 启动和反馈是成对的：进入 `in_progress` 必须对应一次退出的迁移（`pause`/`done`/`fail`/`block`）。
- 记录可穿插在任何阶段，独立于状态机。

### 2.2 状态机与工作循环的关系

状态机定义**合法性**，工作循环定义**典型路径**。

- 状态机保证：任何状态不能被跳过、不能被非法组合。
- 工作循环保证：正常的 agent 行为不会撞上状态机拒绝。

**例**：`task start` 要求所有依赖 done。工作循环的"感知"阶段（`sele next`）只返回就绪 task，因此正常路径下不会触发此拒绝。若 agent 绕过感知直接 start 未就绪 task，状态机拒绝——这是**保护**而非**限制**。

### 2.3 人 vs agent 的循环差异

| 阶段 | Agent | 人（Developer） |
|---|---|---|
| 感知 | `sele next`（拓扑导航） | `sele tree` / `sele status`（全局视图） |
| 启动 | 可自主 `task start` | 可自主 `task start` / `task insert` |
| 推进 | 全流程可自主 | 通常旁观，必要时介入 `step approve` / `task verify` |
| 反馈 | `pause` / `done` / `fail` 自主 | `approve` / `reject` / `archive` 自主 |
| 记录 | `decision record` | 同 |
| **禁区** | 改 plan/line 定义、创建 task、跳过提交 | 无（全权限） |

人的循环更像"审计循环"，agent 的循环更像"执行循环"。二者共享同一状态，但起点和粒度不同。

## 三、实体生命周期模型

### 3.1 生命周期骨架

每个实体经历：**创建 → 活跃 → 终止 → 归档**。

但"终止"在不同实体上含义不同：

| 实体 | 终止态 | 归档后能否复活 |
|---|---|---|
| Plan | `done` / `aborted` | 可 restore（恢复为 active） |
| Line | `done` / `abandoned` | 随 Plan 恢复 |
| Task | `done` | 可 `revive` 回 `todo` |
| Step | `done` / `skipped` | 随 Task 复活，旧 step 只读 |

### 3.2 Task 的"死亡"是相对的

Task 的 `archived` 不是终点。关键区分：

- **活跃的 Task**：可执行、可修改、可暂停。
- **归档的 Task**：不可执行，但**是功能实现本身**，可被唤醒继续扩展。
- **复活的 Task**：回到 `todo`，旧 step 全部只读保留，追加新 step。

**为什么 Task 不真正"死亡"**：task 是功能的载体，功能会演进。归档只是"暂时不做"，不是"永不提及"。这个语义让 sele 支持"功能迭代"而非"一次性任务"。

### 3.3 Step 的"死亡"是绝对的

Step 一旦 `done`，**不可删除、不可重排、不可回退**。

- 可改：title / desc / requires_review（记录事件）
- 不可改：status（done 后）、id、位置（done 后）

**为什么**：step 是"已经发生的动作"，历史不可篡改。可改的只有描述性的元数据，不是事实本身。

### 3.4 归档的边界

归档一个 Plan 意味着：

- 该 Plan 及其所有 Line/Task 从活跃区移出
- 事件日志**不归档**（append-only，全局保留）
- 索引更新，归档内容不参与 `sele next`

**归档不销毁，只移出活跃视野**。任何归档内容仍可被 `sele log` 查询、被 restore 恢复。

## 四、执行轮换模型

### 4.1 轮换的本质

单 agent 单 task 的约束下，"并行"是**逻辑并行**：多个 task 处于 `todo`/`paused`，agent 按需切换。

轮换的原子操作是：

```
暂停当前 + 恢复目标 = 一次状态对交换
```

两者必须**成对发生**，否则破坏 I1。

### 4.2 轮换的三种触发

| 触发 | 语义 | 命令 |
|---|---|---|
| **主动切换** | agent 决定换 task | `sele task start <other>`（自动 pause 当前） |
| **显式暂停** | agent 暂离不切走 | `sele task pause <id> --reason` |
| **插入打断** | 新 task 优先级更高 | `sele task insert ... --pause-current` |

三种触发最后都落到"当前 → paused + 目标 → in_progress"。

### 4.3 轮换的现场保真原则

暂停时必须保真的信息：

| 类别 | 内容 |
|---|---|
| **位置** | 当前 step、该 step 的进度描述 |
| **环境** | git 快照（HEAD、脏文件、diff stat） |
| **意图** | 未解决的问题、恢复提示 |
| **代价** | 已跳过的 task 计数（衡量拖延） |

原则：**恢复时 agent 不依赖任何记忆**。pause_context 是唯一的事实来源。

### 4.4 跳过计数的语义

`skipped_count` 不是"时间"，是"**被轮换无视的次数**"。

- 每次 `sele next` 或 `task start <other>` 未选中此 paused task，+1。
- 计数只增不减，唯一重置方式是 `task keep`（显式确认继续保留）或恢复执行。

**为什么用跳过而非时间**：

- 跳过计数反映"agent 的实际行为偏好"，时间只反映"物理经过"。
- 一个被跳过 5 次的 task 说明 agent 在回避它，值得警示。
- 一个暂停 10 天但从未被跳过的 task 说明 agent 没在工作，不值得警示。

## 五、就绪与推进模型

### 5.1 "就绪"的定义

一个 Task 就绪 ⇔ 同时满足：

| 条件 | 说明 |
|---|---|
| 状态 ∈ {`todo`, `paused`} | 未开始或暂停中 |
| 所有 `depends` 的 task 状态 = `done` | 依赖完成 |
| 其所属 Line 未 `blocked`/`abandoned` | 线未被阻塞/放弃 |
| 其所属 Plan 为 `active` | 计划在推进中 |
| 全局无其他 `in_progress` | 遵守 I1 |

**就绪是动态的**：任何依赖状态变化都会重新计算。已就绪的 task 可能因为新插入的 task 而变得未就绪（新 task 插入到它前面）。

### 5.2 拓扑序的语义

`sele next` 返回**按拓扑序排列的就绪 task 列表**，不是"唯一推荐"。

- 拓扑序保证：如果 T1 依赖 T2，则 T2 一定排在 T1 之前。
- 同层 task 顺序**由创建顺序决定**（隐式 FIFO），不引入优先级。
- 返回列表 ≠ agent 必须按序执行。agent 可任选其一。

**为什么不引入优先级**：

- 优先级是人的决策，不是系统的。
- 引入优先级会让 agent 面对"遵守优先级 vs 按依赖自然推进"的选择困境。
- 优先级如果需要，用 `insert --after` 显式表达：把高优 task 插到前面。

### 5.3 推进的边界

**只有 agent 和人可以推进**。Sele 本身不推进任何状态。

- Sele 不调度、不触发、不轮询。
- 所有状态迁移都由显式命令触发。
- 无后台进程、无定时器、无事件循环。

**意义**：Sele 是**账本**而非**引擎**。它的价值在于记录和校验，不在于驱动。

## 六、暂停与恢复模型

### 6.1 暂停是"一等公民"

`paused` 不是 `in_progress` 的附属态，而是独立的、有完整语义的状态。

区分三个概念：

| 概念 | 状态 | 语义 |
|---|---|---|
| **暂停** | `paused` | agent 主动/被动离开，稍后回来 |
| **阻塞** | `blocked` | 等待外部事件，不是 agent 的选择 |
| **待验收** | `pending_review` | 工作完成，等待人确认 |

三者的恢复路径不同：

- `paused` → agent `resume` 自主恢复
- `blocked` → `unblock`（通常由人触发或外部事件触发）
- `pending_review` → `approve`（必须人触发）

### 6.2 现场快照的完整性

pause_context 的**最小完整集**：

| 字段 | 恢复必要性 |
|---|---|
| `current_step` | 必需，定位进度 |
| `git_snapshot` | 必需，代码现场 |
| `resume_hint` | 必需，意图现场 |
| `open_questions` | 推荐，决策现场 |
| `reason` | 必需，审计现场 |

**省略任何必需字段，恢复时 agent 都无法独立继续**。这是 pause 的完整性判据。

### 6.3 恢复的语义

`resume` 不是"回到暂停时的状态"，而是"**带着暂停时的上下文，重新进入 in_progress**"。

区别：

- 回到暂停时 = 时间旅行（但 git 工作区已变）
- 带着上下文 = 现实中 agent 该做的事

因此恢复时 Sele 打印现场对比（暂停时 vs 现在），让 agent 自行判断是否需要弥补差异。**Sele 不替 agent 做这个判断**。

### 6.4 暂停的代价

长期 paused 的 task 会：

- 占用"跳过计数"（每次被无视 +1）
- 达到阈值后警示
- 但不自动归档、不自动放弃

**设计选择**：宁可让 task 卡在 paused 被警示，也不自动清理。清理是人/agent 的决定，不是系统的。

## 七、约束模型

### 7.1 约束的四层

Sele 的"约束"落在四个层次：

| 层 | 约束什么 | 载体 |
|---|---|---|
| **意图层** | 目标边界 | Plan/Line 的 goal、acceptance |
| **范围层** | 能改什么 | Task 的 `modules` |
| **顺序层** | 何时能做 | `depends`、拓扑序、单活跃约束 |
| **证据层** | 做完要留什么 | 事件日志 |

四层缺一层，"约束"就不完整。

### 7.2 约束的强度分级

| 强度 | 语义 | 违反时的行为 |
|---|---|---|
| **硬约束** | 不可违反 | 命令直接拒绝 |
| **软约束** | 建议遵守 | 警告，允许继续 |
| **审计约束** | 事后记录 | 允许违反，但记录事件 |

**分配**：

| 约束 | 强度 |
|---|---|
| I1 / I2（单活跃） | 硬 |
| 状态机迁移合法性 | 硬 |
| `depends` 满足 | 硬（`task start` 时校验） |
| `modules` 范围 | 软（`module_scope` 配置：warn/block） |
| `requires_review` 的 step | 硬（完成后转 pending_review） |
| review_policy | 硬（决定 done 还是 pending_review） |
| 决策记录 | 审计（不强制但建议） |

### 7.3 约束的作用点

约束在**三个时机**生效：

| 时机 | 检查内容 | 违反后果 |
|---|---|---|
| **写操作前** | 状态合法性、依赖满足、范围 | 命令拒绝 |
| **读操作时** | 漂移检测、一致性 | 返回警告或阻断 |
| **验收时** | 验收点满足、review_policy | 转 pending_review |

**没有"事后补救"机制**。约束要么在写时拦住，要么在验收时拦住，不会事后追究。

## 八、验收模型

### 8.1 完成的定义（Definition of Done）

"完成"在三层有不同的判定：

| 层 | 完成条件 |
|---|---|
| **Step** | 执行动作结束 + 若需审核则人工 approve |
| **Task** | 所有 step done/skipped + 所有 acceptance 满足 review_policy |
| **Plan** | 所有 line/task done + 计划级 acceptance 通过 |

**每一层的完成不是"所有下层完成"的同义词**，还要加上本层的 acceptance。

### 8.2 验收点的两种验证者

| 验证者 | 语义 | 可信度 |
|---|---|---|
| `agent` | agent 自验 | 低（自说自话） |
| `human:<name>` | 人工验证 | 高 |

**自验和人工验都可记录**，但 review_policy 决定"什么算完成"：

- `strict`：只有 human 验算完成
- `lenient`：agent 验即可，人工异步复审
- `mixed`：按验收点粒度区分（`requires_human`）

### 8.3 pending_review 的语义

`pending_review` 不是"已完成"也不是"未完成"，而是"**agent 认为完成，等待人确认**"。

- 一旦进入 pending_review，agent 不再推进这个 task。
- 人可以 `approve`（→ done）或 `reject`（→ 回 in_progress）。
- 待验收 task 不阻塞其他 task 推进（除非其他 task 依赖它）。

**关键**：pending_review 是"人的决策点"，不是"agent 的暂停点"。agent 的工作到此结束，剩下的是人的责任。

### 8.4 验收不评判质量

Sele 不评判"做得好不好"，只记录"是否满足声明的验收标准"。

- 验收标准是**人/agent 自己声明的**，不是 Sele 定义的。
- 验收标准是**可判定**的（要么 pass 要么 fail），不是主观的。
- 质量高低是人的判断，Sele 只保证"声明的标准被验证了"。

## 九、审计模型

### 9.1 审计的三要素

| 要素 | 载体 | 保证 |
|---|---|---|
| **发生了什么** | 事件 op + entity | 有记录 |
| **为什么发生** | `reason` 字段 | 有动机 |
| **当时现场** | `context` 字段 | 有背景 |

三要素缺一，审计就不可信。

- 只有 what：知道发生了什么，不知道为什么
- 只有 what+why：不知道为什么当时这样判断（缺 context）
- 三要素齐：任何第三方都能还原当时情境并做独立判断

### 9.2 决策记录的本质

"决策记录"不是独立于状态迁移的机制，而是**状态迁移自带的 reason 字段**。

- 普通迁移（如 `step done`）的 reason 是简短说明
- 关键决策（如"选 JWT 不选 session"）用 `sele decision record` 记录更详细的 reason + context

二者本质相同：都是"为某个动作留下动机和背景"。区别只是粒度和显式程度。

### 9.3 日志的 append-only 语义

事件日志一旦写入，**永不修改、永不删除**。

- `sele log compact` 不是删除，是**归档到独立文件**。
- 归档的日志仍可查询，只是不在主文件里。
- 任何"修正"是通过**新事件**实现的，不是修改旧事件。

**例**：某事件记错了 reason，正确做法是：

```
新事件：op: correction, entity: <原实体>, 
        context: {corrects: <原事件id>, correct_reason: "..."}
```

而不是改原事件。这保证了历史完整性。

### 9.4 重放的边界

Sele 保证"事件可被重放来重建状态"，但不保证"重放能恢复现场"。

- 能重建：状态机迁移、属性变化、依赖关系
- 不能重建：git 工作区、agent 当时的心理状态、未记录的判断

**重放是审计工具，不是恢复工具**。真正的恢复依赖 git commit。

## 十一、漂移与协调模型

### 11.1 漂移的本质

漂移是"**Sele 认为的 git 状态**"与"**git 实际状态**"的不一致。

根源：Sele 不控制 git，git 可被外部操作。Sele 只能**检测**，不能**阻止**。

### 11.2 漂移的六种类型（按危险度）

| 类型 | 现象 | 危险度 | 原因 |
|---|---|---|---|
| D1 | HEAD 前进 | 低 | 正常提交 |
| D2 | HEAD 回退 | 高 | reset |
| D3 | HEAD 分叉 | 极高 | checkout 其他分支 |
| D5 | commit 被改写 | 高 | rebase / amend |
| D6 | 分支切换 | 中 | checkout |

**低危类型默认自动处理，高危类型默认阻断**。配置可调。

### 11.3 协调（Reconcile）的语义

Reconcile 不是"修复漂移"，而是"**让 Sele 承认现实**"。

三个动作：

| 动作 | 语义 |
|---|---|
| `remap` | 现实变了但内容一致，把引用指向新位置 |
| `invalidate` | 现实变了且内容也变，承认旧状态失效 |
| `keep_audit` | 保留旧记录作审计，但不参与状态判定 |

**协调的主动权在人**。Sele 只负责：

1. 检测到漂移
2. 展示影响范围
3. 提供候选动作
4. 执行人的决策
5. 记录协调事件

Sele **不会自动 reconcile**，因为协调涉及"承认什么已不存在"，这是价值判断。

### 11.4 一致性的层级

Sele 保证的一致性分三层：

| 层 | 保证 | 不保证 |
|---|---|---|
| **写时一致** | 每次写操作前检测，漂移则拒绝 | 外部 git 操作本身 |
| **读时一致** | 每次读操作前检测，漂移则告警 | 检测后的状态立即正确 |
| **最终一致** | 通过 reconcile 恢复一致性 | 自动 reconcile |

**明确承诺**：Sele 不能"永远一致"，只能"永远知道不一致"并给出恢复路径。

---

## 十三、归档与复活模型

### 13.1 归档的两层语义

| 层 | 归档什么 | 目的 |
|---|---|---|
| **Plan 归档** | 整个计划的活跃状态 | 移出视野，保留完整 |
| **Task 归档** | 单个 task | 功能完成但可扩展 |

二者独立：一个 Plan 归档，其下所有 Task 一并归档；一个 Task 归档，其所属 Plan 不变。

### 13.2 复活的语义

**复活不是"恢复归档时的状态"**，而是"**以归档内容为基线，在当前状态下继续**"。

- 旧 step 只读保留（历史不可篡改）
- 新 step 追加（从头开始编号 S6、S7...）
- `revive_base` 决定是回看旧基线（`archived`）还是基于当前（`current`）

**为什么默认 current**：现实中"复活一个旧 task"时，代码库早已漂移。基于当前 HEAD 继续是常态，回看旧基线是例外。

### 13.3 归档的不可逃避性

归档后，task **不再参与**：

- `sele next` 导航
- 跳过计数
- 暂停警告
- 依赖图（除非显式 revive）

但**仍参与**：

- `sele log` 查询
- `sele tree` 展示（可过滤）
- 审计链的完整性

**归档是"移出活跃视野"，不是"移出记忆"**。

---

## 十四、权限模型

### 14.1 权限的三个切面

| 切面 | 决定什么 | 载体 |
|---|---|---|
| **角色** | agent vs developer | 调用者身份 |
| **操作类型** | 读 / 写 / 破坏 | 命令分类 |
| **约束强度** | 硬 / 软 / 审计 | 约束层级 |

权限 = 角色 × 操作 × 约束的三维组合。

### 14.2 权限的语义边界

| 权限级别 | 语义 | 例子 |
|---|---|---|
| **完全禁止** | 命令拒绝执行 | agent 不能 `git push` |
| **受限允许** | 满足条件才执行 | agent 可 `git commit` 但需 active task/step |
| **完全允许** | 无额外约束 | 读操作对双方开放 |

**"完全允许"很少**。绝大多数命令都有某种约束，只是强弱不同。

### 14.3 为什么 agent 不能改 Plan/Line

Plan/Line 是**意图的载体**，代表"人要达成什么"。

- Agent 可以执行意图，不能修改意图。
- Agent 可以建议修改（通过 `decision record`），不能直接改。

**边界原则**：agent 拥有"执行权"和"记录权"，人拥有"定义权"和"审批权"。

### 14.4 破坏性操作的最终控制权

`git reset --hard`、`git rebase`、`git push --force` 这类命令：

- **agent 永远不可执行**（无论约束松紧）
- **developer 需二次确认**
- **Sele 永不自动执行**

**理由**：这类操作影响范围超出 Sele 记录范畴，一旦执行，Sele 只能"事后检测"而不能"事前阻止"。把最终控制权留在人手里是唯一合理的边界。

---

## 十五、引用与标识模型

### 15.1 两套 ID

每个实体有两套标识：

| 类型 | 例 | 可变性 | 用途 |
|---|---|---|---|
| **uid** | `tsk_01H2X...` | 不可变 | 文件存储、跨引用、内部索引 |
| **语义 ID** | `T1` | 可变 | 人类使用、agent 命令、日志展示 |

**双 ID 的原因**：

- 语义 ID 可读，但会因重构/改名而变化。
- uid 稳定，但不可读。
- 文件按 uid 命名，改名不动文件；人按语义 ID 操作，不感知 uid。

### 15.2 引用解析

一个逻辑引用（如 `T1`）可能在不同 plan 下存在同名。解析顺序：

1. 当前上下文的 plan/line 内查找
2. 全局唯一则直接命中
3. 多义则要求显式全限定（`plan.line.T1`）

**上下文是隐式的引用解析依据**。`sele line switch` 设置了上下文后，`sele task start T1` 才不会有歧义。

### 15.3 引用的一致性

任何引用（在 depends、事件中）都应指向**实体本身**而非文件路径。

- 引用用 uid 定位（稳定）
- 展示用语义 ID（可读）
- 存储用 uid → 文件的映射（索引）

**文件路径不是引用，是实现的产物**。系统的任何逻辑都不应该依赖文件路径。

---

## 十六、上下文模型

### 16.1 上下文的两个层级

| 层 | 语义 | 载体 |
|---|---|---|
| **Plan 上下文** | 当前在哪个 Plan 里工作 | `sele plan switch` |
| **Line 上下文** | 当前在哪个 Line 里工作 | `sele line switch` |

上下文是**简写解析的依据**，不是"当前在做什么"。当前在做什么由 `in_progress` 的 task 决定。

### 16.2 上下文的持久性

上下文存储在本地（`.sele/cache/context.json`），不纳入版本控制。

- 每个开发者/agent 有独立上下文。
- 上下文的丢失不影响任何状态。
- 上下文只是**简写便利**，不是事实来源。

### 16.3 上下文的语义边界

上下文**不约束**操作：

- 设置了 Plan 上下文后，仍可 `sele task start <other-plan-task> --full`。
- 上下文只是简写的默认值，不是权限的范围限制。

**上下文是"默认"，不是"边界"**。

---

## 十七、视图模型

### 17.1 四类视图

Sele 提供四种读视图，语义不同：

| 视图 | 语义 | 回答什么 |
|---|---|---|
| **status** | 当前完整状态 | 现在是什么样 |
| **next** | 可执行集合 | 我下一步能做什么 |
| **tree** | 结构视图 | 整体是什么样 |
| **log** | 历史视图 | 过去发生了什么 |

四种视图**互不替代**：status 不告诉你下一步，next 不告诉你整体，tree 不告诉你历史，log 不告诉你当前。

### 17.2 status 的语义

`sele status` 返回**当前 plan 的完整状态**：

- 所有 line 的状态
- 所有 task 的状态（含 paused、blocked、pending_review）
- 阻塞点（哪些 task 因为依赖未满足不能推进）
- 警告（跳过计数超标）

status 是**静态快照**，不推理、不推荐。

### 17.3 next 的语义

`sele next` 返回**当前可执行的 task 列表**（拓扑序）：

- 已过滤掉依赖未满足的
- 已过滤掉非 `todo`/`paused` 的
- 不排序、不推荐、不预测

next 是**动态结果**，随状态变化而变化。

### 17.4 tree 的语义

`sele tree` 返回**结构视图**（Plan → Line → Task → Step）：

- 默认展示活跃的
- `--all` 包含归档
- 用于人类快速理解整体结构

tree 是**人类视图**，不是 agent 视图。agent 用 next。

### 17.5 log 的语义

`sele log` 返回**历史事件**（按时间过滤、按实体过滤）：

- 支持 `--decisions` 只看决策
- 支持 `--task <id>` 只看某 task
- 支持 `--replay` 打印完整时间线

log 是**时间视图**，不是状态视图。

## 十八、错误与异常模型

### 18.1 错误的四个级别

| 级别 | 语义 | 例子 |
|---|---|---|
| **用户错误** | 参数/用法错误 | 不存在的 task id |
| **状态冲突** | 违反状态机 | 在 todo 上执行 done |
| **约束违反** | 违反约束 | 依赖未满足时 start |
| **系统异常** | 数据损坏/环境问题 | 漂移阻断、文件损坏 |

四级错误处理方式不同：

- 用户错误：提示 + 退出码 2
- 状态冲突：提示 + 退出码 3
- 约束违反：提示 + 退出码 3（或 4 若涉及 git）
- 系统异常：提示 + 退出码 4/5/6

### 18.2 异常的不可忽略性

任何异常**不得静默处理**：

- 不允许"尽力执行后忽略异常"
- 不允许"异常后进入未定义状态"
- 不允许"用默认值掩盖异常"

**理由**：Sele 是约束工具，静默异常会让约束失效。异常必须显式暴露，让人/agent 决策。

### 18.3 部分失败的语义

当一次命令涉及多个状态变更时（如批量归档），部分失败的处理：

- **有事务性的场景**：整体撤销（如归档的两阶段）
- **无事务性的场景**：逐项记录成功/失败，明确报告

**没有"尽力而为"模式**。要么全成功，要么明确失败，不留在半状态。

## 十九、概念间的关系图

```
                         ┌──────────────┐
                         │   意图层      │
                         │ Plan / Line  │
                         └──────┬───────┘
                                │ 定义"要做什么"
                                ▼
                         ┌──────────────┐
                         │   执行层      │
                         │ Task / Step  │
                         └──────┬───────┘
                                │ 产生
                                ▼
                         ┌──────────────┐
                         │   证据层      │
                         │ 事件日志      │
                         └──────┬───────┘
                                │ 校验
                                ▼
                         ┌──────────────┐
                         │   一致性层    │
                         │ 漂移检测      │
                         │ Reconcile    │
                         └──────────────┘
```

**四层的推进关系**：

1. 意图层定义目标和边界
2. 执行层在边界内推进
3. 每步推进产生证据
4. 证据校验保证一致性

任何一层失效都会传导：意图不清 → 执行无向；执行无据 → 证据缺失；证据不一致 → 系统不可信。

## 二十、设计取舍的总结

| 取舍点 | 选择 | 放弃 |
|---|---|---|
| 时间 vs 顺序 | 顺序驱动 | 时间阈值、定时调度 |
| 自动 vs 显式 | 显式命令 | 后台推进、隐式状态变更 |
| 引擎 vs 账本 | 账本 | 调度器、执行器 |
| 中心 vs 分布 | 中心化状态 | 分布式并发（单 agent 单 task） |
| 硬约束 vs 软约束 | 分层 | 全硬或全软 |
| 自验 vs 人验 | 分层 | 全自验或全人验 |
| 自动恢复 vs 人工协调 | 人工协调 | 自动 reconcile |
| 语义 ID vs uid | 双 ID | 单一 ID |
| 深度嵌套 vs 扁平 | 类型扁平 + hash 分桶 | 目录嵌套 |
| Git 融合 vs 代理 | 代理 | 深度融合或完全隔离 |

这些取舍构成 Sele 的**身份**。改变任何一条，Sele 就不是 Sele 了。

---

## 结语

规范 v1.0 回答"有什么命令、有什么字段、有什么状态"。
本文回答"这些命令、字段、状态意味着什么、为什么这样设计、边界在哪里"。

前者是**接口契约**，后者是**心智契约**。

任何 Sele 实现（无论什么语言、什么架构）都必须满足本文的所有概念约束，才能被称为"符合 Sele 规范"。
